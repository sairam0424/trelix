# Batch API Provider Feasibility — Azure OpenAI & AWS Bedrock — 2026-09-18

Triggered while trying to live-verify PR #317's OpenAI Batch API feature end-to-end: no real `OPENAI_API_KEY` was available in this environment, but real Azure OpenAI and AWS Bedrock credentials were already configured. Before spending that credential budget, this asked the prior question directly: can either provider's own batch capability be used in place of raw OpenAI's, and if so, what would it take to wire into trelix's existing `OpenAIEmbedder.submit_batch()`/`poll_batch()` pattern (persisted `embed_batch_jobs` table, `BatchJobTerminalError`/`BatchJobIncompleteError` split)?

Six independent `deep-research` runs (5 search angles → fetch top sources → 3-vote adversarial claim verification → cited synthesis each), three per provider — implementation contract, integration path against trelix's actual classes, and production best practices. One run (Azure implementation contract) hit a `StructuredOutput` retry-cap failure on its first pass and had to be resumed; its output was verified for real content (not the placeholder failure output) before use. The critical open question the integration-path run flagged — whether Azure batch supports embeddings at all — was independently confirmed by directly fetching Microsoft's own current batch documentation rather than trusting a single research pass.

---

## Azure OpenAI Batch — not viable, platform limitation

**Confidence: HIGH — do not build. Azure OpenAI's Batch API does not support embeddings requests at all.** Verified directly against Microsoft's current batch how-to doc (8,496 words, `ms.date` 2026-05-13, updated 2026-06-05): every JSONL example on the entire page — chat, vision, structured outputs — targets `/chat/completions`; there is not one embeddings example anywhere, and the docs state the system auto-detects only "chat completions or the responses API" from the input file. The FAQ entry "Can I use the batch API for embeddings models?" is a literal copy-paste bug — its answer verbatim repeats the unrelated "fine-tuned models aren't supported" answer — but combined with the total absence of embeddings examples across an otherwise exhaustive page, the real answer is clearly no. This is a platform gap, not an integration difficulty: no amount of correct client wiring on trelix's side changes what endpoint Azure's batch service accepts.

Everything else researched is context for if Azure ever adds this, not a current path:
- **API shape**: `client.files.create(purpose="batch")` → `client.batches.create(input_file_id, endpoint, completion_window="24h")`. No model/deployment field at the batch level — it lives only inside each JSONL line's `body.model`, which must be the **deployment name**, not the model name; every line in one file must target the same deployment (`model_mismatch`/`model_not_found` otherwise).
- **SDK quirk**: Microsoft's current (2026) recommended pattern bypasses `AzureOpenAI` entirely — plain `OpenAI()` client pointed at a versionless `https://<resource>.openai.azure.com/openai/v1/` base URL, no `api_version`. The older `AzureOpenAI`/`AsyncAzureOpenAI` classes still work but require an explicit `api_version` (raise `ValueError` otherwise) and — notably — exclude `/batches` and `/files` from their deployment-URL-prefixing regardless of which client is used.
- **Integration path** (moot given the blocker, but confirmed): job-status enum and error shapes are byte-identical to raw OpenAI, so trelix's `BatchJobTerminalError`/`BatchJobIncompleteError` split would need zero changes if this endpoint existed.
- **Best practices/gotchas** (relevant if trelix ever batches chat/completions traffic through Azure, unrelated to embeddings): 50% discount vs. Global Standard pricing; the 24h window is a target, not an SLA — jobs are never force-killed, they run to completion or cancellation and only completed work is billed; quota is a separate "enqueued tokens" pool (not TPM-based) varying enormously by model/tier/region — e.g. `gpt-4.1` Global batch: 5B tokens (Enterprise/MCA-E) / 200M (Default) / 50M (monthly credit-card) / 90K (MSDN) / N/A (Students), with Data Zone batch ~10x lower for the same model; file caps of 200MB (1GB via Bring-Your-Own-Storage) and 100K requests/file, 500 files (no expiration) or 10,000 (expiration set) per resource; a real open `openai-python` SDK bug causes large (>200-300MB) result downloads to fail mid-stream; two platform gotchas — Azure-CLI-deployed resources get malformed endpoint subdomains that break global batch, and UTF-8-BOM-encoded `.jsonl` files get rejected with a misleading generic error instead of an encoding-specific one.

## AWS Bedrock Batch Inference — buildable, scoped to Titan only

**Confidence: HIGH — technically buildable, but only for `BedrockTitanEmbedder`, and requires genuinely new infrastructure.** `CreateModelInvocationJob`/`GetModelInvocationJob` live on the `bedrock` control-plane client — never on `bedrock-runtime`, the real-time client `_BedrockEmbedderBase` currently uses. Unlike OpenAI's file-upload flow, Bedrock batch requires **S3 URIs for both input and output**; there is no inline-body option. Input is JSONL (`recordId` + `modelInput`), output mirrors it with `modelOutput` (or an error object on failure), plus a `manifest.json.out` summary reporting record/token counts.

**Critical finding: Cohere Embed is not in AWS's supported-models list for batch inference at all.** Only **Titan Text Embeddings V2** supports it, and only in exactly 12 single-region locations. `BedrockCohereEmbedder` is excluded from this feature by AWS itself — it isn't a trelix design choice.

What adding `submit_batch`/`poll_batch` to `_BedrockEmbedderBase` would concretely require:
- An **S3 bucket** for input/output staging — infrastructure trelix has no precedent for today.
- A **dedicated IAM service role** (`roleArn`), distinct from whatever credentials the caller already uses, with its own trust policy plus S3 read/write permissions. A misconfigured role doesn't fail synchronously at job creation — it surfaces later as a `Validating → Failed` status transition, since Bedrock validates S3 access as part of that state.
- **Job status is a 10-value enum**: Submitted, Validating, Scheduled, Expired, InProgress, Completed, PartiallyCompleted, Failed, Stopped, Stopping. Maps cleanly onto trelix's existing terminal/non-terminal split — the 5 non-terminal states → `BatchJobIncompleteError`, Failed/Expired/Stopped → `BatchJobTerminalError` — but **`PartiallyCompleted` is new**, a soft-success terminal state with no OpenAI equivalent, and needs its own explicit design decision (treat as success-with-warnings surfaced per-record, or as incomplete requiring a retry of only the failed records).
- A single orchestration layer (S3 staging, IAM role, status-mapping) can be shared, but per-model JSONL payload construction and response parsing still need per-model logic, since Titan's request/response shape differs from Cohere's — even though only Titan would ever actually exercise the batch path.

**Best practices**: 50% discount vs. real-time `invoke_model` pricing for supported models; job-size and concurrency quotas are non-uniform per-model and per-region (5GB–100GB range, not a flat cap); AWS recommends **EventBridge's "Batch Inference Job State Change" event** over polling (progress counters can read 0 at submission and lag up to a minute); partial failures are handled per-record via the output JSONL and `manifest.json.out`, not job-wide.

## Bottom line

**Azure is a dead end for embeddings specifically** — not a design or integration problem on trelix's side, a platform limitation. The batch endpoint doesn't accept embeddings requests at all.

**Bedrock is real, scoped, buildable work** — but narrower than it sounds: only `BedrockTitanEmbedder` would ever qualify, and it requires standing up genuinely new infrastructure (S3 bucket + IAM role + trust policy) with no precedent in trelix today, unlike the OpenAI-direct path which needed none of that, plus a new design decision for the `PartiallyCompleted` terminal state. It's the more tractable of the two by a wide margin simply because it's possible at all — but it's feature-sized effort, not a quick port of the existing OpenAI Batch API pattern.

No code shipped from this research — these are written findings only, feeding a future decision on whether to build Bedrock Titan batch support.
