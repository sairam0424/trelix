# Chunking-strategy spike — 2026-09-18

**Phase 6-style research spike.** No code ships from the main finding below; one small, independently-justified fix is scoped separately at the end.

## Question

trelix's `Chunker.build_chunks()` (`src/trelix/indexing/chunker.py`) builds exactly one `Chunk` per parsed `Symbol` (function/method/class) — this is the "Function" chunking strategy in the taxonomy of a controlled empirical study that found per-symbol chunking underperforms every alternative tested. Does that finding mean trelix should change its chunking strategy?

## What the research found (verified via a 94-agent adversarial-verification research pass; 19/25 claims confirmed, 6 refuted)

**Source:** arXiv:2605.04763, Wu/Gong/Jahangirova/Zhang (King's College London, submitted May 2026), "How Does Chunking Affect Retrieval-Augmented Code Completion? A Controlled Empirical Study" — 864 experimental settings across 4 chunking strategies × 4 retrievers × 5 generators × 9 parameter configs, on RepoEval and CrossCodeEval.

- **Confirmed, high confidence:** Function/per-symbol chunking (trelix's current approach) underperforms Declaration (signature-only), Sliding Window (fixed-size line windows), and cAST (AST split+merge) by 3.57–5.64pp Exact Match on RepoEval, Cliff's δ=−1.0 — a fully consistent effect across every retriever/generator/split combination tested. Function chunking is never Pareto-optimal on the cost-quality frontier.
- **Confirmed, high confidence, important nuance:** the margin between the three *non*-Function strategies is narrow (0.38–2.07pp) — Sliding Window edges out overall, but cAST actually wins on the Java subset of CrossCodeEval. This is not "Function is bad, X is the clear winner" — it's "Function is bad, the other three are roughly tied."
- **Confirmed, high confidence, most load-bearing finding for trelix:** cross-file context length — not chunking strategy — is the single most influential parameter the study found. Doubling the context window from 2,048→8,192 tokens produced up to 4.2pp EM improvement, exceeding even retriever choice; chunk size itself had a weaker, non-monotonic effect (≤1.9pp).
- **Confirmed:** cAST's own paper (arXiv:2506.15655, CMU/Augment Code, EMNLP 2025) separately reports +4.3 Recall@5 (RepoEval retrieval) and +2.67 Pass@1 (SWE-bench), varying by retriever backbone (not uniform).
- **Confirmed:** the paper's own Discussion (§6.4) proposes structure-aware chunking as a *context-compression* mechanism (what to keep/discard) rather than as the retrieval unit itself — an open future-work direction, no follow-up found yet (paper is ~4.5 months old).
- **Refuted / unverifiable — do not treat as fact:** specific claims that Cursor uses sibling-merging or that Greptile embeds one docstring per AST node both failed independent verification (0-3 votes). Only Continue.dev has verifiable published guidance, and it explicitly recommends *against* full AST-based chunking by default (framed as "most exact, but most complex," not worth the cost for most users) — and doesn't have a dedicated one-symbol-per-chunk mode to "move away from" in the first place. The premise that production RAG code tools have already moved off per-symbol chunking for this reason is **not substantiated**.

## What this means for trelix specifically

trelix is not a bare RAG-completion pipeline of the kind this study benchmarks — it already has **three** mechanisms that address the gap the study attributes to narrow per-symbol chunks, at layers other than "change the primary chunking unit":

1. **Multi-leg RRF fusion + call-graph/dataflow expansion** (`expand_with_call_graph`, `expand_with_dataflow`) already pull in a symbol's callers/callees/dataflow-adjacent code at query time — a different route to the study's own strongest finding (cross-file context length matters more than chunking strategy).
2. **`ContextualChunker`** already prepends an LLM-generated summary to each chunk — addresses a similar "isolated chunk lacks context" problem to cAST's merge, without changing chunk cardinality.
3. **MGS3 multi-granularity sub-chunk indexing** (`src/trelix/indexing/multi_granularity.py`, `multi_granularity_enabled`, off by default) is *already a shipped, structure-aware chunking mechanism* directly on point for this question: it walks the tree-sitter AST of each symbol's own (un-truncated) body and extracts block- and statement-level sub-chunks into a dedicated `sub_chunks` table, retrievable via an opt-in `sub_chunk_search_enabled` RRF leg and consumed by the extractive-compression layer. This is not cAST's sibling-*merge* (it doesn't combine multiple small symbols into one chunk) but it is real prior art for "don't force one rigid chunking granularity" — built and shipped, just gated behind two flags that default to off.

Given this, and given the narrow, non-decisive margin between the three winning strategies in the study plus the unverified state of any real production adoption of full AST split+merge chunking, adopting cAST's sibling-merge wholesale is a large, cross-cutting change for an uncertain, likely-already-partially-captured gain: it would break the current 1-chunk-to-1-symbol cardinality assumed throughout `SearchResult`, the reranker reconstruction sites, and `graph_context` attribution — the exact class of "silently drops a field across reconstruction sites" bug this session already found three separate times in adjacent code this same week.

**Verdict: LOW-MEDIUM confidence that a full AST split+merge chunking redesign is worth building right now.** Not because the underlying research is weak (it's well-verified) — because the trelix-specific case for it is diluted by (a) three already-existing, overlapping mechanisms, one of which (MGS3) is structurally the closest existing analog and already shipped, (b) narrow margins among the actual alternatives, and (c) a real, structurally-similar-to-recent-bugs implementation risk for an uncertain gain.

## Two lower-risk follow-ups worth flagging (neither implemented in this PR)

1. **`_truncate_chunk()` still destructively discards content by default.** Symbols exceeding `max_tokens_per_chunk` (default 512) have their excess body silently dropped from the *primary* chunk — the one used by the always-on vector/BM25 legs. MGS3's block/statement sub-chunks (when enabled) recover *some* of this via a separate retrieval leg, but a query that would match well against the oversized symbol as a linear whole still only sees the truncated primary chunk by default, since MGS3 is off by default. Splitting into a second sequential chunk instead of truncating is a strict improvement with no cardinality-assumption change elsewhere (still N chunks cleanly trace to symbols, just possibly >1 per oversized symbol) — small, isolated, `chunker.py`-scoped.

3. **Addendum (2026-09-19): the split fix in (1) has a known, accepted retrieval-fusion trade-off.** Now that oversized symbols are split into multiple sequential chunks instead of truncated, `src/trelix/retrieval/fusion.py`'s `reciprocal_rank_fusion` can silently drop one split piece's distinct content from a fused result set: `_fusion_identity()` dedupes on `(indexed_file.path, chunk.symbol_id)`, not on a piece-level identifier, so if two pieces of the same split symbol both rank in one query's ranked list, only the first-seen piece survives the `if identity not in best_result` collapse — the second piece's content is dropped from that query's fused output even though it was successfully retrieved. This is not a new failure mode: it is the same identity-key limitation that already applied to MGS3's opt-in sub-chunk leg (`sub_chunk_search_enabled`, default off) — a rare, explicitly opt-in edge case. What this diff changes is *frequency*, not existence: the chunker's split path is unconditional and default-on for any oversized symbol on the always-on vector/BM25 legs, so the same collapse mechanism now applies on the mainline path instead of only behind an opt-in flag. This is deliberately **not fixed here**: `fusion.py`'s own docstring and `_fusion_identity()` explicitly forbid adding a second dedupe pass and document real regression history (EXE-02, a cross-repo erasure bug) from a prior attempt to key identity differently. A correct fix would need to extend the identity key to include a piece-level discriminator (e.g. `chunk_id`) for known split pieces while leaving intra-symbol collapsing behavior unchanged everywhere else — tracked as a separate follow-up, not part of this PR.
