## Executive Summary — What v4.0.0 Should Actually Contain

Ranked by how concrete/actionable the evidence is:

1. **Fix `pydantic-settings` now, independent of v4.0.0** — CVE-2026-58203 (Moderate, symlink traversal in `NestedSecretsSettingsSource`) sits inside trelix's *current, unbounded* floor (`>=2.3.0`, no ceiling), meaning dependency resolution could land on a genuinely vulnerable version (2.12.0–2.14.1) today. This is a floor pin, not a breaking change — no need to wait for v4.0.0.
2. **Bump Python floor to `>=3.12`** — well-justified by both official EOL timing (3.11 is security-only since Apr 2024, EOL Oct 2027) and ecosystem convention (SPEC 0's 3-year rule marks 3.12 as its own drop-candidate starting next month). Not urgent, but v4.0.0 is the natural vehicle since it's the only release allowed to break things.
3. **Re-evaluate the two roadmap MCP items with corrected facts**: SEP-2322/`InputRequiredResult` is **already Final and merged** (not draft) as of protocol 2026-07-28 — implementing it is a real, scoped, breaking schema change (new `resultType` field, restricted to 4 request types). Streaming tool-result *content*, by contrast, is genuinely still vaporware (SEP-2998, open/unsponsored, no reference implementation) — don't block v4.0.0 on it.
4. **Reconsider the "JetBrains plugin" backlog item's scope entirely** — JetBrains shipped native MCP client support in IDE 2025.2+. The roadmap item may not need a custom plugin at all, just a docs page. This needs a cheap follow-up before committing engineering time.
5. **Migrate off `openai`/`anthropic` SDK floors before their breaking majors bite** — both shipped intentional breaking v3.0.0/v1.0.0 releases in the last month (httpx2 transport, Anthropic Python floor→3.10, removed legacy APIs). trelix's LLM abstraction layer also has no schema slot for the "reasoning" content-block type every provider now ships (Anthropic `thinking`, Bedrock `reasoningContent`) — this is a real abstraction gap, not just a version bump.
6. **`tree-sitter`/`numpy`/`rich`/`typer` all have breaking majors sitting above trelix's current floors** that were never absorbed — each needs its own migration line-item (see Dependencies section).
7. **The "Multi-modal indexing" research-backlog item is a genuine differentiator, not catch-up** — none of 6 major competitors (Cursor, Copilot, Aider, Cody, Continue, Zed) index diagrams/images as searchable RAG artifacts today.

**Coverage gaps this research did NOT close** (flag for a follow-up pass before finalizing v4.0.0 scope): google-genai/Vertex AI and litellm SDK changes (no confirmed findings either research field); 9 of 16 Python dependencies got no CVE/upgrade-path coverage (PyYAML, sqlite-vec, openai, tiktoken, pathspec, defusedxml, networkx, tenacity, httpx, structlog — silent, not clean); LangChain `BaseRetriever`/LlamaIndex retriever-interface stability (asked twice across two research fields, answered in neither); JetBrains plugin effort estimate and Marketplace requirements.

## Dependency-floor upgrade paths
**Question posed:** Research upgrade paths for trelix's (a Python code-intelligence/RAG-for-code engine, current version 3.2.5, requires-python>=3.11) core dependency floors ahead of its next release, v4.0.0, the only release trelix's own roadmap allows to make breaking changes. Current floors from pyproject.toml: tree-sitter>=0.23, tree-sitter-language-pack>=1.13.0, PyYAML>=6.0, sqlite-vec>=0.1.6, openai>=1.35.0, tiktoken>=0.7.0, numpy>=1.26.0, pathspec>=0.12.1, typer>=0.12.0, rich>=13.7.0, pydantic>=2.8.0, pydantic-settings>=2.3.0, defusedxml>=0.7.1, networkx>=3.3.0, tenacity>=8.5.0, httpx>=0.27, structlog>=24.1.0. For each: what's the current latest stable release, has any major/breaking version shipped since this floor was set, and what would migrating to latest concretely require? Cite official changelogs/release notes/PyPI for every claim.

**Summary:** Of trelix's 16 pinned dependency floors, verified evidence covers 7: tree-sitter-language-pack, tree-sitter (py-tree-sitter), numpy, pydantic, pydantic-settings, typer, and rich. Three of these (tree-sitter-language-pack>=1.13.0, pydantic>=2.8.0, pydantic-settings>=2.3.0) have NOT crossed a major/breaking version boundary since their floors were set and can be bumped to current latest (1.17.0 / 2.13.5 stable with 2.14.0 in beta / 2.15.0 respectively) with no forced migration. Four have shipped genuine breaking releases since their floors: tree-sitter (>=0.23) via py-tree-sitter 0.25.0 (Query methods moved to a new QueryCursor class) and 0.26.0 (removed Language.version, Language.query(source), timeout_micros methods); numpy (>=1.26.0) via NumPy 2.0.0 (Jun 2024, first major release since 2006 — ABI break, NEP 50 type-promotion changes, undocumented API removals); typer (>=0.12.0) via 0.26.0 (vendored Click, dropping support for Click-specific plugins/custom types); and rich (>=13.7.0) via two major bumps, 14.0.0 and 15.0.0, though 15.0.0's only documented breaking change (dropping Python 3.8 support) doesn't block trelix since it already requires Python>=3.11. No verified findings exist yet for PyYAML, sqlite-vec, openai, tiktoken, pathspec, defusedxml, networkx, tenacity, or httpx, or structlog, leaving those as open research gaps ahead of the v4.0.0 breaking-change window.

### Findings

**[HIGH]** tree-sitter-language-pack (floor >=1.13.0): latest stable is 1.17.0 (released 2026-09-09/10). No entry between 1.13.0 and 1.17.0 is marked as a breaking change — the changelog's only ever 'Breaking change' entry (get_language()/get_parser() returning native binding types) predates the 1.13.0 floor. Upgrading trelix's floor to 1.17.0 requires no migration work.
- Vote: 3-0 (x2 underlying claims), 2-1 (x1 underlying claim)
- Evidence: Confirmed via PyPI JSON API + PyPI HTML page + GitHub release history + raw CHANGELOG.md all agreeing on 1.17.0 as latest (repo renamed kreuzberg-dev -> xberg-io). Grep of the full 2251-line changelog found exactly one bolded 'Breaking change' marker, at 1.9.0-rc.52 (2026-06-16), which is chronologically before the 1.13.0 floor (2026-07-19); every entry strictly between 1.13.0 and 1.17.0 was checked and carries no breaking-change label.
- Sources: https://github.com/kreuzberg-dev/tree-sitter-language-pack/blob/main/CHANGELOG.md, https://pypi.org/project/tree-sitter-language-pack/, https://github.com/xberg-io/tree-sitter-language-pack (renamed org, redirect target)

**[HIGH]** tree-sitter / py-tree-sitter (floor >=0.23): has shipped two breaking releases since the floor — v0.25.0 (query execution moved off Query onto a new QueryCursor class; e.g. Query.captures removed, replaced by QueryCursor.captures with an added progress_callback param) and v0.26.0 (removed Language.version, Language.query(source), Parser.timeout_micros, QueryCursor.timeout_micros, each with a documented replacement). Both releases mark changes with an explicit '!' breaking-change convention. Latest stable is 0.26.0.
- Vote: 3-0 (x3 underlying claims)
- Evidence: Both release pages fetched directly and confirmed verbatim: 0.25.0 lists 12 items under Removals marked with '!' (Query.captures, Query.matches, Query.timeout_micros, etc. all moved to QueryCursor), with the notes explicitly stating 'Breaking changes are marked with !'; 0.26.0 lists Language.version, Language.query(source), Parser.timeout_micros, and QueryCursor.timeout_micros as removed with named replacements. PyPI confirms 0.26.0 is the current latest published version, above trelix's tree-sitter>=0.23 floor. Migrating past 0.23 to 0.26.0 concretely requires: replacing any Query.captures/matches/timeout_micros calls with QueryCursor equivalents, and swapping Language.version/Language.query(source) usages for Language.abi_version/Query(language, source).
- Sources: https://github.com/tree-sitter/py-tree-sitter/releases/tag/v0.25.0, https://github.com/tree-sitter/py-tree-sitter/releases/tag/v0.26.0, https://pypi.org/pypi/tree-sitter/json

**[HIGH]** numpy (floor >=1.26.0): NumPy 2.0.0 (released 16 Jun 2024) is a major breaking release — the first major release since 2006 — that breaks C-API/ABI compatibility (packages built against NumPy 1.x will ImportError on NumPy 2.0), changes type-promotion rules via NEP 50 (e.g. np.float32(3) + 3. now returns float32 instead of float64; mixed dtype arithmetic can produce different-precision results than under 1.26.x), and includes API changes some of which didn't previously emit deprecation warnings in 1.26.x. Official migration guide, release notes, and tracking issue (numpy#24300) exist as concrete resources.
- Vote: 3-0 (x6 underlying claims)
- Evidence: Official NumPy migration guide and 2.0.0 release notes fetched directly and quoted verbatim on the ABI break (PyArray_Descr struct became more opaque, causing ImportError for binaries built against 1.x), the NEP 50 type-promotion change (precision of scalars now preserved consistently, can change output dtype/precision for mixed-dtype ops), and undocumented-deprecation API changes. numpy.org/news independently corroborates: 212 contributors, 1078 PRs, 11 months of development, explicitly labeled 'Major/breaking release.' Since trelix's floor (numpy>=1.26.0, Sept 2023) predates 2.0.0 (June 2024), pip can currently resolve numpy 2.x under the existing floor, carrying all of the above breaking changes into any environment that installs latest.
- Sources: https://numpy.org/doc/stable/numpy_2_0_migration_guide.html, https://numpy.org/doc/stable/release/2.0.0-notes.html, https://numpy.org/news, https://github.com/numpy/numpy/issues/24300 (tracking issue)

**[HIGH]** pydantic (floor >=2.8.0): no v3.0.0 or any major/breaking version has shipped since the floor — version progression is strictly sequential through v2.10, 2.11, 2.12, 2.13 (latest stable v2.13.5) into v2.14 pre-releases (2.14.0a1/b1/b2, still beta as of the research date). No migration is forced by upgrading the floor to latest 2.x.
- Vote: 3-0

## LLM provider SDK & model landscape
**Question posed:** Research what has changed in the 5 LLM provider SDKs that trelix (a Python code-intelligence engine, current version 3.2.5) wraps in its LLM backend layer — the openai Python SDK (trelix's floor: openai>=1.35.0), the anthropic Python SDK, boto3/botocore (AWS Bedrock Converse API), google-genai (Vertex AI), and litellm — that matters for trelix's next major release, v4.0.0 (the only release allowed breaking changes per trelix's roadmap). For each provider: new or deprecated model IDs, new streaming response formats, new tool-call/structured-output APIs, any breaking SDK version bump, and anything the provider now offers that a generic ChatMessage/ChatResponse/ToolCallResponse abstraction layer couldn't express when built against openai>=1.35.0-era APIs. Cite official SDK changelogs/docs for every claim.

**Summary:** Across the five provider SDKs trelix wraps, the two most release-critical facts for v4.0.0 are: (1) both openai-python (v3.0.0, 2026-08-12) and anthropic-sdk-python (v1.0.0, 2026-08-20) shipped major, intentionally breaking version bumps that swap the default HTTP transport to "httpx2" and (for Anthropic) also raise the Python floor to 3.10+, remove the legacy Text Completions API, drop temperature/top_p/top_k from Messages methods, remove tool-runner compaction_control, and make Bedrock region configuration mandatory — all of which trelix's dependency floor (openai>=1.35.0) and its Bedrock backend must account for. (2) Every provider has independently added a "reasoning"-shaped content-block type that has no slot in a classic ChatMessage/ChatResponse/ToolCallResponse schema built in the pre-reasoning-model era: Anthropic's `thinking`/`redacted_thinking` blocks (with `signature`, and a "don't filter only on thinking" gotcha), and Bedrock Converse's `reasoningContent` block (`reasoningText.text` + tamper-evident `signature`, plus `redactedContent`) which also appears as a third ConverseStream delta kind alongside text/toolUse. Both Anthropic and Bedrock also now expose dedicated structured-output surfaces (Anthropic's `output_config.format`, Bedrock's `outputConfig.textFormat` + `toolSpec.strict`) that sit outside tool-calling and would need new abstraction fields. OpenAI's Responses API (if trelix adopts it) uses a fundamentally different typed-SSE streaming model than Chat Completions' delta-chunk format. Anthropic also retired seven legacy model IDs and introduced a new "5" model generation (Sonnet 5, Opus 5, Fable 5.1, Mythos 5.1) with a new tokenizer that inflates token counts ~30% for Sonnet 5. Notably, no confirmed claims surfaced for google-genai/Vertex AI or litellm — this research pass did not establish what changed in those two providers, which is a gap trelix's next research/prep cycle should close before finalizing the v4.0.0 breaking-change list.

### Findings

**[HIGH]** openai-python v3.0.0 (2026-08-12) is an intentional breaking release: HTTPX2 becomes the default HTTP client and `httpx` is no longer installed automatically; custom HTTPX clients/transports must migrate to HTTPX2 equivalents or use a temporary legacy escape hatch.
- Vote: 3-0
- Evidence: GitHub release-please tooling tags this as a ⚠ BREAKING CHANGES entry verbatim: 'HTTPX2 is now the default HTTP client, and httpx is no longer installed automatically... See the HTTPX2 migration guide.' Corroborated by openai/openai-python/httpx2.md (TLS trust-store shift from certifi to OS trust store), developers.openai.com/api/reference/python, and the Agents SDK changelog requiring openai>=3.0.0,<4. Vote 3-0.
- Sources: https://github.com/openai/openai-python/blob/main/CHANGELOG.md, https://github.com/openai/openai-python/blob/main/httpx2.md

**[HIGH]** OpenAI's Responses API streams typed server-sent events (response.created, response.output_text.delta, response.completed, etc.) instead of Chat Completions' delta-chunk format — a breaking change for any streaming abstraction that adopts Responses.
- Vote: 3-0
- Evidence: Official migration guide states streaming consumers must branch on event type, listing response.created/response.output_text.delta/response.completed/error, and explicitly flags reusing Chat Completions delta handlers as a common migration error. Corroborated by Azure OpenAI's migration guide and third-party migration writeups describing the same event set. Vote 3-0. Chat Completions remains supported per the same source, so this is conditional on Responses adoption, not forced.
- Sources: https://developers.openai.com/api/docs/guides/migrate-to-responses

**[HIGH]** anthropic-sdk-python v1.0.0 (2026-08-20) is an intentional breaking release: HTTP layer moves from httpx to httpx2 (Pydantic-team fork), Python floor raised to 3.10+, and the SDK removes long-deprecated surface — the legacy Text Completions API, `temperature`/`top_p`/`top_k` on Messages methods, and the tool runner's `compaction_control` — while `AnthropicBedrock` now raises an error if no AWS region is configured instead of silently defaulting to us-east-1.
- Vote: 3-0
- Evidence: CHANGELOG.md dates v1.0.0 to 2026-08-20 with breaking-change note pointing to MIGRATION.md, which verbatim confirms each sub-change (httpx2 move, Python 3.10 floor matching pyproject.toml, removal of client.completions.create()/HUMAN_PROMPT/AI_PROMPT, removal table for temperature/top_p/top_k across create/stream/parse/tool_runner, removal of tool_runner(compaction_control=...) in favor of server-side compaction, and Bedrock region now raising ValueError at construction). Independently corroborated by a third-party blog dated two days after release. Vote 3-0 on both underlying claims (merged).
- Sources: https://github.com/anthropics/anthropic-sdk-python/blob/main/CHANGELOG.md, https://raw.githubusercontent.com/anthropics/anthropic-sdk-python/main/MIGRATION.md, https://platform.claude.com/docs/en/release-notes/overview

**[HIGH]** Anthropic shipped a dedicated Structured Outputs capability on the Messages API — public beta Nov 14 2025 (beta header structured-outputs-2025-11-13), GA Jan 29 2026 (SDK v0.77.0) — guaranteeing schema conformance via constrained decoding, and relocated the request parameter from `output_format` to `output_config.format` (Bedrock/Microsoft Foundry remain beta-only).
- Vote: 3-0
- Evidence: v0.77.0 CHANGELOG entry verbatim adds 'Structured Outputs in the Messages API' and migrates 'output_config rather than output_format' in the same release. release-notes/overview separately dates the beta (Nov 14 2025) and GA (Jan 29 2026, Claude API only) milestones and states the param move explicitly. structured-outputs docs page confirms output_format is now legacy/transitional. This is a structured-output API surface not present in openai>=1.35.0-era abstractions. Vote 3-0 on both merged sub-claims.
- Sources: https://github.com/anthropics/anthropic-sdk-python/blob/main/CHANGELOG.md, https://platform.claude.com/docs/en/release-notes/overview, https://platform.claude.com/docs/en/build-with-claude/structured-outputs

**[HIGH]** Anthropic's model lineup changed materially through 2026: new IDs Claude Sonnet 5 (claude-sonnet-5, launched June 30 2026, new tokenizer producing ~30% more tokens for identical text, $2/$10 per MTok introductory pricing), Claude Opus 5 (July 24 2026), Claude Fable 5.1 and Claude Mythos 5.1 (Sept 1 2026); meanwhile seven older IDs were retired and now error on invocation — Claude Opus 4.1 (Aug 5 2026), Claude Sonnet 4 and Claude Opus 4 (June 15 2026), Claude Haiku 3 (Apr 20 2026), Claude Sonnet 3.7 and Claude Haiku 3.5 (Feb 19 2026), Claude Opus 3 (Jan 5 2026).
- Vote: 3-0
- Evidence: anthropic-sdk-python CHANGELOG v0.114.0 (2026-06-30) adds claude-sonnet-5 support verbatim. ## MCP protocol evolution
**Question posed:** Research the current state of the Model Context Protocol (MCP) specification, specifically: (1) has "SEP-2322" and its "InputRequiredResult" pattern (for a tool's input-wait/elicitation behavior) been finalized or merged into the official MCP specification, and what would implementing it actually require of an MCP server? (2) what is the current status of streaming tool responses in the MCP spec — supported now, or still proposed? (3) what is the current official MCP protocol version, and what other spec changes have landed since the "mcp>=1.24.0,<2.0 / fastmcp>=3.4.0"-era Python SDK versions that a FastMCP-based Python MCP server should be aware of for its next major version bump? Cite the official MCP specification site/GitHub repo and any SEP (spec enhancement proposal) documents directly.

**Summary:** SEP-2322 ("Multi Round-Trip Requests," which defines the InputRequiredResult pattern) has reached Final status and is fully merged/normative in the official MCP specification as of the current protocol version, 2026-07-28 — it is not merely proposed. It replaces server-initiated requests (sampling/elicitation/roots) with servers returning an InputRequiredResult (a new required resultType: "complete"|"input_required" field on all results) and clients retrying the original request with inputResponses attached; this is restricted to GetPromptRequest, ReadResourceRequest, CallToolRequest, and GetTaskPayloadRequest, and is explicitly called out as a breaking change from all Streamable HTTP behavior in 2025-03-26 through 2025-11-25 (which also removed protocol-level sessions/Mcp-Session-Id and the GET SSE stream endpoint entirely). Streaming of actual tool-result content, by contrast, remains unimplemented and only proposed: SEP-2998 ("Partial Tool Results") is an open, unsponsored Draft SEP with no reference implementation, and a related SEP-2664 proposal was closed without merging; the pre-existing SSE notification-before-final-response mechanism (progress/log messages) is unchanged plumbing dating to 2025-03-26 and does not chunk the result content itself. The MCP Python SDK (mcp/fastmcp) already shipped v2.0.0 implementing 2026-07-28 while remaining backward compatible with every earlier revision from the same server, replacing ctx.elicit()-style server-to-client callbacks with a Resolve()/InputRequiredResult-driven flow (ctx.elicit() is retained only for legacy connections) — a next major SDK version should track this resultType/InputRequiredResult schema plus other landed SEPs referenced in the SDK's own notes (SEP-2663 Tasks extension, SEP-2577 sampling/roots deprecation, SEP-2567 session removal).

## JetBrains plugin feasibility
**Question posed:** Research feasibility of building a JetBrains (IntelliJ Platform — IntelliJ IDEA/PyCharm) plugin that talks to a local MCP (Model Context Protocol) server over stdio/JSON-RPC, as an IDE-integration parallel to an existing VS Code extension that already does this (spawns an MCP server binary as a child process, talks MCP JSON-RPC over stdio, and exposes search/ask/hover-provider features backed by MCP tool calls). Specifically research: (1) the current IntelliJ Platform Plugin SDK's support for spawning/talking to an external process via MCP or JSON-RPC — including any of JetBrains' own recent native MCP support announcements (JetBrains AI Assistant, or platform-level MCP client support), and whether LSP4IJ or a similar existing bridge plugin already solves part of this problem, (2) realistic Kotlin vs Java plugin development effort for a search/ask/hover-provider feature set, (3) JetBrains Marketplace listing/publishing requirements and review process, including any installation-count gates analogous to some marketplaces requiring a minimum install count before featured/verified review. Cite JetBrains' own official Plugin SDK docs, Marketplace docs, and any official MCP-support announcements directly.

**Summary:** The IntelliJ Platform already gives you everything needed on the "spawn a local process and talk to it over stdio" side: GeneralCommandLine + OSProcessHandler are the documented, current SDK primitives for launching and monitoring an external child process, and LSP4IJ proves this pattern works in production for stdio JSON-RPC-style traffic (LSP). More importantly, JetBrains itself has already shipped native, first-party MCP support since IDE version 2025.2 in both directions: AI Assistant's MCP client supports STDIO transport (spawns the MCP server as a subprocess exactly like the VS Code extension does), and a bundled, enabled-by-default MCP Server plugin lets the IDE itself expose tools to external MCP clients (Claude Code, Codex, VS Code, GitHub Copilot CLI) — with the older standalone mcp-jetbrains proxy now officially deprecated in favor of this built-in support. LSP4IJ, the closest existing "bridge plugin," does not itself solve MCP today — its shipped capability is scoped strictly to LSP/DAP-over-stdio — and its only MCP-related work is an open, unreviewed, unmerged pull request (#1582) that would make LSP4IJ an MCP *server* (reverse of what a client-spawning plugin needs), so it cannot be treated as an existing solution. Critically, none of the surviving verified claims address development-effort (Kotlin vs Java) or JetBrains Marketplace publishing/review/install-count-gate questions — those sub-questions returned no verified evidence in this pass.

### 4. LangChain / LlamaIndex retriever-interface stability

**Summary:** Neither LangChain's nor LlamaIndex's core custom-retriever abstract interface has changed, in method name, signature, or constructor requirements, within roughly the last 12 months, so an existing thin adapter subclass built against either framework should NOT need updating for that reason. ### Net effect on Phase 3/5/6 scope

- **Phase 3 (zero-source-change dependency bumps)** should now also absorb: `openai` (breaking v2.0.0 tool-output-typing change + v3.0.0 httpx2, both already tracked in Phase 5), `pathspec` (breaking v1.0.0 — dropped Py3.8, removed `_match_file()`, renamed `gitwildmatch`→`gitignore`; trelix doesn't subclass pathspec internals per earlier exploration, but worth a grep-confirm before bumping), `tenacity` (breaking v9.0.0 shipped 24 days after trelix's 8.5.0 floor — need to check the `statistics` attribute isn't used), `structlog` (breaking — dropped Py3.8/3.9, floor already >=3.12 so moot), `tiktoken` (breaking v0.8.0 dropped Py3.8, moot). **PyYAML, sqlite-vec, networkx, httpx got no confirmed findings this round either** — still open.
- **Phase 5 (LLM abstraction)**: litellm already ships a `reasoning_content: str` + `thinking_blocks: list[{type, thinking, signature}]` pair on its message type, populated identically across ~11 providers via per-provider transformers with the explicit design goal "a consistent format for thinking blocks between Anthropic and Bedrock." **This directly validates and should inform `ReasoningBlock`'s design in Phase 5.1** — consider mirroring litellm's exact field names (`reasoning_content`/`thinking_blocks`) instead of inventing new ones, for interop. Also: google-genai's Gemini reasoning surface ("thought signature") differs structurally from Anthropic/Bedrock — in the classic `generateContent` API it's a `thought: bool` flag + `thought_signature: bytes` attached to an ordinary `Part`, NOT a distinct content-block type, and reasoning/answer text arrive as the same delta kind (distinguished only by the `thought` flag) — a naive `chunk.text`-concatenating stream reader would silently interleave them. If Vertex is ever added to the `ReasoningBlock` model, this needs its own `kind` and its own streaming-delta handling, not a reuse of Anthropic/Bedrock's pattern. Also flags a **forward-compat risk**: google-genai's own PyPI README already warns v3.0.0 will remove Automatic Function Calling from direct `generate_content` calls and recommends pinning `<3.0.0` — Vertex's floor (`google-genai>=1.0.0`, unbounded) has the same "unpinned ceiling ahead of an announced breaking release" shape as the openai/anthropic issue Phase 0 already fixed.
- **Phase 3b (LangChain/LlamaIndex adapters)**: not needed. Neither framework's core retriever interface changed in the last 12 months — LangChain's `BaseRetriever._get_relevant_documents` and LlamaIndex's `BaseRetriever._retrieve` are both unchanged, and LangChain even ships a backward-compat shim tolerating the older 2-arg signature. The only real LangChain v1 change (legacy retrievers moved to a new `langchain-classic` package) doesn't touch the abstract-method contract trelix's adapters implement.
