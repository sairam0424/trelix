# trelix v2.6.x Scale Backlog — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the 4 remaining v2.6.0 "Scale & Performance" backlog items — Qdrant Cloud readiness, incremental per-symbol embedding, parallel read-only BM25 connections, and Linux/Windows ARM64 binary releases.

**Architecture:** Four independent plans, each shippable on its own PR. Plan A adds Cloud-specific connection options (gRPC, timeout/retry) to the already-Cloud-capable `QdrantVectorStore` and extends the existing manual `migrate-vectors` CLI to also carry `sub_chunks`/file-summary vectors it currently drops. Plan B adds a `content_hash` column to the `symbols` table and diffs newly-parsed symbols against stored ones before delete+re-embed, skipping unchanged symbols entirely. Plan C adds a small pool of read-only SQLite connections (leveraging the WAL mode already enabled) that `bm25_search` draws from instead of the single shared writer connection. Plan D adds two new CI matrix entries using GitHub's existing free ARM64-native runners (`ubuntu-24.04-arm`, `windows-11-arm`) — no cross-compilation needed.

**Tech Stack:** Python 3.11+, `qdrant-client>=1.9.0`, SQLite3 stdlib + FTS5, PyInstaller, GitHub Actions. No new external dependencies for Plans A-C; Plan D adds no new dependencies either (uses existing GitHub-hosted runner labels).

```python
"""
Read-only SQLite connection pool for parallel BM25 reads.

Database opens exactly one writer connection with check_same_thread=False,
shared across the whole process — every bm25_search() call funnels through
that single connection object regardless of how many application threads
call it, so concurrent FTS5 MATCH queries cannot truly execute in parallel
even though the database is already in WAL mode (which permits many
concurrent readers at the SQLite-engine level).

This pool opens a small fixed number of SEPARATE connections, each using
SQLite's read-only URI mode (file:{path}?mode=ro) plus PRAGMA query_only,
so read-heavy deployments can draw an independent connection per concurrent
BM25 query instead of serializing on the shared writer connection.

Opt-in via StoreConfig.bm25_read_pool_size (default 0 = disabled, meaning
Database.bm25_search() uses the existing single-connection path unchanged).
"""

from __future__ import annotations

import queue
import sqlite3
from contextlib import contextmanager
from pathlib import Path
from typing import Iterator


class ReadOnlyConnectionPool:
    """A fixed-size pool of read-only SQLite connections against one WAL-mode
    database file. acquire() blocks until a connection is available if the
    pool is momentarily exhausted (pool_size concurrent readers max)."""

    def __init__(self, db_path: Path, pool_size: int = 4) -> None:
        self._db_path = db_path
        self._pool_size = pool_size
        self._available: queue.Queue[sqlite3.Connection] = queue.Queue()
        self._connections: list[sqlite3.Connection] = []
        for _ in range(pool_size):
            conn = sqlite3.connect(
                f"file:{db_path}?mode=ro", uri=True, check_same_thread=False
            )
            conn.execute("PRAGMA query_only = ON")
            conn.row_factory = sqlite3.Row
            self._connections.append(conn)
            self._available.put(conn)

    @contextmanager
    def acquire(self) -> Iterator[sqlite3.Connection]:
        conn = self._available.get()
        try:
            yield conn
        finally:
            self._available.put(conn)

    def close_all(self) -> None:
        for conn in self._connections:
            conn.close()
        self._connections = []
```

**Scope note on Plan A's "auto-migration":** per the research, true *automatic* migration (detecting a backend-config change at startup and transparently moving data with zero user action) does not exist today and would be a much larger architectural change (a `MigrationManager` invoked from `Retriever`/`Indexer` startup, with attendant risk of silently kicking off a long-running data transfer inside what today is an instant config read). This plan scopes "Qdrant Cloud integration" to the two concretely actionable, safely-scoped pieces confirmed missing in the research (gRPC/timeout Cloud connection options; the migration command's incomplete embedding-source coverage) rather than building a new auto-triggered migration subsystem sight-unseen. If true zero-touch auto-migration is wanted, it should be its own follow-up plan scoped after Task A-2 ships and its coverage gaps are closed.
